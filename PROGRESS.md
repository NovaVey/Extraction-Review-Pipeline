## Phase 2 — Ingest

### Summary
PDF ingest pipeline (page rasterization, text-layer extraction, OCR fallback, sha256 hash-dedupe, Supabase Storage upload, `documents`/`pages` row writes), the `POST /schemas`, `POST /batches`, `GET /batches/:id`, and `POST /batches/:id/documents` routes, and two operator scripts to seed the three doc-type schemas and bulk-ingest the full 60-doc corpus.

### Files created/touched

### Decisions
- **`@napi-rs/canvas` bumped `^0.1.65` → `^1.0.0`.** `pdfjs-dist` v6's renderer calls `ctx.fill(path)` with a `Path2D` argument; 0.1.x's Canvas 2D implementation doesn't support that overload (`"Value is none of these types String, Path"`). Re-verified against both new (`pageRender.ts`) and existing (Phase 1's `make-synthetic-docs.ts`) consumers after the bump — no regressions.
- **OCR trained-data: added `@tesseract.js-data/eng` as a pinned dependency, rather than tesseract.js's CDN default.** tesseract.js normally fetches English trained data from `cdn.jsdelivr.net` at runtime, which this sandbox's egress policy blocks (`403`, same class of restriction as Supabase/Railway in Phase 0). `@tesseract.js-data/eng` ships the identical file as a plain npm package (`registry.npmjs.org` — already reachable, same host `npm install` itself uses); pointing `createWorker`'s `langPath` at its local `node_modules` path removes the CDN dependency entirely, in this sandbox **and** in production (no more runtime reliance on jsdelivr's uptime). Confirmed via `AskUserQuestion` before adding — a new dependency outside the originally-approved stack list. Also set `cacheMethod: 'none'`: without it, tesseract.js additionally writes a *decompressed* copy of the trained-data file into the current working directory on first use, which briefly left a stray untracked `eng.traineddata` (~5MB) at the repo root during testing; since `langPath` already reads instantly from a local, permanent path, that cache added no value and is now suppressed at the source. The stray file itself was deleted (never committed) and `*.traineddata` added to `.gitignore` defensively.
- **`api/tsconfig.json` root cause fix, not a workaround: `"lib": ["ES2022"]`.** `uploadObject()`'s `fetch(url, { body: someBuffer })` failed to typecheck with confusing "Buffer not assignable to BodyInit... missing URLSearchParams properties" errors. Root cause: neither `api/tsconfig.json` nor the shared `tsconfig.base.json` set `lib` explicitly, so TypeScript's target-based default (`ES2022` → implicitly `DOM` + `DOM.Iterable` too) pulled in `lib.dom.d.ts`'s own `fetch`/`BodyInit` globals alongside `@types/node`'s, and the two competing declarations didn't structurally agree on typed-array bodies. `/api` is pure backend code with no browser surface, so scoping it to `lib: ["ES2022"]` (no DOM) removes the phantom second declaration entirely — `/web`'s own independent tsconfig (Vite's standard split config) still has DOM and is untouched.
- **Root `package.json` root cause fix: added `"type": "module"`.** Every script under `/scripts` uses `import.meta.url` (ESM-only), but the root `package.json` never declared `"type": "module"` — under `moduleResolution: NodeNext`, that makes TypeScript treat root-level `.ts` files as CommonJS-intended by default (`tsc` even flagged it explicitly once `/scripts` got real typecheck coverage: `import.meta not allowed in CommonJS output`). `tsx`'s runtime loader is permissive enough that this never surfaced as a runtime failure (Phase 1's `make-synthetic-docs.ts` ran fine despite it), but it's a real latent inconsistency, not just a new-script problem — fixed at the root rather than worked around per-file.
- **`scripts/tsconfig.json` added**, extending the shared base, `include: ["**/*.ts"]`, wired into the root `typecheck` script. Justified now (wasn't in Phase 1) because `seed-schemas.ts`/`ingest-corpus.ts` are the first root-level scripts to import across the `/scripts` ↔ `api/src` boundary — exactly the boundary the `"type": "module"` bug above was hiding in.
- **Storage upload stays on plain `fetch`, no `@supabase/supabase-js`** — continues the Phase 0 decision; `uploadObject()` is one more REST call in the same style as `pingStorage()`.
- **Storage path convention:** `batches/{batchId}/{sha256}/original.pdf` and `batches/{batchId}/{sha256}/pages/{pageNumber}.png` — content-addressed by sha256 *within* a batch (scoped per-batch, not globally, so one batch's later retention purge can't delete another batch's copy of the same bytes) and upserted (`x-upsert: true`), so retrying a partially-failed ingest is always safe.
- **`documents.hasTextLayer` = true only if *every* page has a text layer; `documents.ocrRequired` = true if *any* page doesn't.** Matches how this was already verified against the corpus in this session (`hasTextLayer` cross-checked 0 mismatches against `manifest.json`'s `difficultyGroup !== 'scanned'`, which is itself a whole-document label).
- **Known limitation, not fixed this phase:** text-layer detection is whole-page, not per-field. The "handwriting-in-one-field" edge-case docs (Phase 1) embed only *one* field as a rasterized image inside an otherwise normal text PDF — the page's other fields keep `hasTextLayer` comfortably above the 5-character threshold, so OCR fallback never triggers for that page, and that one field's value is only recoverable from the page image, not from `pages.textContent`. Extraction (Phase 3+) will need to reason from the rendered page image for cases like this regardless of the page-level flag; flagging here so it isn't mistaken for a bug later.
- **`/samples` corpus was regenerated once during this phase** (`npm run gen:samples`), while verifying the `@napi-rs/canvas` bump didn't break Phase 1's generator — same composition (60 docs, 20/20/20 by doc type, 15/15/15/15 by difficulty group, 10 in the dev subset), fresh `Math.random()`-fabricated field values throughout. The generator's own design treats this as expected/harmless (its header comment notes `Math.random()` is deliberately unseeded, "this is a one-shot local script"), and every Phase 2 test in this session runs against the current on-disk corpus successfully — committing the regenerated files rather than reverting to Phase 1's original random draw.
- **`POST /batches/:id/documents` only accepts `application/pdf`** — page images are always derived from the uploaded PDF by this pipeline, never uploaded directly, so accepting image mimetypes here would be misleading.
- **`scripts/ingest-corpus.ts` groups the corpus into one batch per doc type** (`"invoice corpus"`, `"receipt corpus"`, `"purchase_order corpus"`), matching the schema-per-batch relationship (`batches.schemaId` is a single FK) and the fact each doc type has its own schema from `seed-schemas.ts`.
- **Bug found and fixed on the user's Windows machine, not visible in this sandbox: `pageRender.ts`'s `GlobalWorkerOptions.workerSrc`.** pdfjs-dist loads it via a dynamic `import()`, which needs a real URL. A raw `path.resolve()` result happens to work on POSIX (no scheme ambiguity) but fails on Windows — a drive letter like `C:\Users\...` gets misparsed as a URL scheme (`"Setting up fake worker failed: ... Received protocol 'c:'."`), and every one of the 60 documents failed on the first `ingest-corpus.ts` run as a result. Fixed by wrapping the resolved path in `pathToFileURL(...).href` (`node:url`), which is correct on every platform — not a Windows-only branch. `standardFontDataUrl` (same file) turned out not to need the same fix: it's consumed via `fs.readFile()` internally (traced through pdfjs-dist's source to confirm rather than assume), which accepts raw OS paths fine. Re-ran the full test suite in this sandbox after the fix — no regressions — then the user re-ran `ingest-corpus.ts` on Windows: `ingested=60 deduped=0 failed=0`.

## Phase 3 — Extract

### Summary
LLM-based structured extraction: one Anthropic Messages API call per sample (`SAMPLE_COUNT=3` samples per document), each given every page's extracted text *and* rendered image, constrained to a JSON Schema built from the document's `extraction_schemas.fields`. Samples are combined by self-consistency voting — the value most samples agree on is stored, and the agreement fraction becomes the field's confidence — writing `extractions`, `field_values`, and `field_value_rows` rows. Wired into `POST /documents/:id/extract` and `scripts/extract-devset.ts`. Hard-restricted to the 10-doc dev subset (`documents.inDevSubset`), enforced in code, not just by convention.

### Files created/touched
- `api/src/extract/schema.ts` — `buildExtractionJsonSchema(fields)`: maps `extraction_schemas.fields` (`FieldSpec[]`) to the JSON Schema passed as `output_config.format.schema`.
- `api/src/extract/anthropic.ts` — `extractSample()`: builds the per-page text+image content blocks, calls `client.messages.parse()` with `output_config.format` (structured output) and `thinking: {type: 'adaptive'}`, no `temperature`.
- `api/src/extract/run.ts` — `extractDocument(documentId)`: the orchestrator (DB reads, N parallel samples, majority-vote confidence, basic per-field validation, DB writes). Exports `pickMajority`/`validateField` directly for unit testing.
- `api/src/lib/storage.ts` — added `downloadObject()` (Phase 2 only had `uploadObject`/`pingStorage`) to fetch page PNGs back out of Storage for the extraction request.
- `api/src/routes/extract.ts` — `POST /documents/:id/extract`, registered in `app.ts`.
- `scripts/extract-devset.ts` — bulk-runs extraction over every `inDevSubset: true` document.
- `api/test/extract/{schema,run}.test.ts` — see Testing below.

### Decisions
- **Structured Outputs (`output_config.format`), not tool-use, for extraction.** `client.messages.parse()` validates/parses the response against the schema automatically (confirmed by reading the SDK's actual `parser.js`: for a plain `json_schema` format — not just a Zod-derived one — it falls back to `JSON.parse()` on the response text, so this works without a Zod dependency). This is the tool built for "extract into a schema," not a fit-for-purpose-but-wrong tool.
- **Nullability requires `anyOf`, not a `type` array — found via a real 400, not assumed.** The first live request with `currency: {type: ['string','null'], enum: [...]}` was rejected: `"Enum value 'USD' does not match declared type '['string', 'null']'"`. Fixed by expressing nullable fields as `{anyOf: [{type: 'string', enum: [...]}, {type: 'null'}]}` instead — every field is still marked `required` (must be present in the response), but its value can legitimately be `null` for a field genuinely absent from the document (the `missing_required_field` synthetic edge case is exactly this case, and is meant to produce a real, non-error null, not a fabricated value).
- **Every page is sent as both extracted text and a rendered image**, not one or the other. Text alone would fail outright on the 15 scanned docs and the handwriting edge case (no usable text layer, by design); images alone would waste tokens re-deriving what OCR/the text layer already got right on the other 45. The system prompt explicitly tells the model the image is ground truth when the two disagree.
- **The Phase 0 temperature question is resolved.** `claude-sonnet-5` still rejects a non-default `temperature` with a 400 (re-confirmed via the `claude-api` skill). `extractions.temperature` (`NOT NULL`) stores the *configured* `EXTRACTION_TEMPERATURE` value for audit purposes — it documents the intended sampling setting without ever being sent on the request. Real sample-to-sample diversity for the multi-sample design instead comes from adaptive thinking's implicit variance (on by default for `claude-sonnet-5`), which a live test confirmed still produces genuinely differing outputs across samples.
- **Confidence in Phase 3 is exactly one signal: sample agreement.** `field_values.confidenceParts` is deliberately an extensible jsonb bag (`{sampleAgreement: 0.67}` today); the `/confidence` directory scaffolded since Phase 0 is where later signals (validator results, cross-field consistency, historical accuracy) get composed into a calibrated score. `field_values.status` is set to `'pending'` for every field this phase — auto-accept/needs-review routing against each field's `autoAcceptThreshold` is a confidence/review-phase decision, not an extraction one.
- **`field_values.validatorStatus` (`NOT NULL`) is basic type-format checking, not business-rule validation.** Per field type: `date` must `Date.parse()`, `money` must be numeric after stripping symbols, `enum` must be one of the field's `enumValues`, everything else just non-empty; `null` → `'missing'`. Deliberately does *not* check cross-field consistency (e.g. subtotal+tax=total) — the two_currencies edge case exists specifically to exercise that kind of check later, in the confidence/review phases, not here.
- **Money values are stored two ways**, discovered from a real extraction, not assumed: the model transcribes amounts as literally printed (`"$106.81"`, matching a live test against `invoice_clean_01.pdf`), but `manifest.json`'s gold-set ground truth stores the stripped form (`"106.81"`). `rawValue` keeps what the model actually said; `normalizedValue` strips currency symbols/commas for `money` fields specifically, so it's comparable to gold-set values later. Other field types pass through unchanged for now.
- **`inDevSubset` is enforced inside `extractDocument()` itself**, not just in the script that happens to only query dev-subset rows — so the one guaranteed choke point both the route and the bulk script share can't be bypassed by calling the route directly on a non-dev-subset document. Matches the explicit project rule restricting extraction to 10 documents to control API cost.
- **`FieldSpec`/`ColumnSpec` types are declared locally in `api/src/extract/schema.ts`**, structurally identical to but not imported from `scripts/fieldSpecs.ts` — `/api` should stay deployable without `/scripts` existing at runtime, and jsonb columns come back untyped from Drizzle regardless of where the TS type is declared, so there's no real coupling benefit to importing across that boundary in this direction (unlike Phase 2's scripts → api imports, which go the natural "operator script drives the app's own code" direction).
- **`PROMPT_VERSION` (`'v1'`)** stored on every `extractions` row — bumped whenever the system prompt or schema-building logic changes in a way that would make old and new extractions non-comparable for eval/gold-set purposes later.
- **`GET /documents/:id/extraction` added** (`api/src/routes/documents.ts`) to actually read extraction results back — there was no way to inspect what got extracted otherwise. Returns the *most recent* extraction for a document (ordered by `startedAt DESC` — extraction isn't deduplicated like ingestion, so a document can have several `extractions` rows over time) plus its `field_values`, with `field_value_rows` nested under table-type fields. Deliberately excludes the full `rawResponses` blob from the response (could be large; exposes only `sampleResponseCount` as a cheap audit signal that all N samples were actually stored). Built via a small Workflow: one agent implemented it, then two independent agents reviewed it in parallel — a general code reviewer, and a second agent that re-derived the correct join/ordering logic from `schema.ts` from scratch *before* looking at the implementation, to catch a subtly-wrong query without being anchored by it. Both passed the implementation; the code reviewer's one real finding (an unguarded `as unknown[]` cast on the untyped `rawResponses` jsonb column, which would 500 on a malformed row instead of degrading gracefully) was fixed before commit.

## Phase 4 — Confidence Scoring

### Summary
Replaces Phase 3's placeholder confidence/status handling (`confidenceParts: {sampleAgreement}` only, `status: 'pending'` on every field regardless of `autoAcceptThreshold`) with a real scoring model: a new `api/src/confidence/` module combines sample agreement, per-field/per-cell format validation, and cross-field business-rule reconciliation (subtotal+tax=total, line-item sum vs subtotal, quantity×unit_price=amount) into a single confidence number, then decides `auto_accepted` vs `needs_review` against each field's configured `autoAcceptThreshold`. Applies to both `field_values` and, for the first time, individually to each `field_value_rows` line item — rows previously just inherited the parent table's agreement verbatim with no validation of their own cells.

### Files created/touched
- `api/src/confidence/validate.ts` — `validateValue(type, enumValues, rawValue)`: generalizes Phase 3's `validateField` to also validate individual line-item cell values (added a real `'number'` case, previously ungoverned); `stripMoneySymbols`/`parseMoney`.
- `api/src/confidence/score.ts` — `computeConfidence(input)`: the scoring formula (see Decisions); `decideStatus(confidence, autoAcceptThreshold)`.
- `api/src/confidence/crossFieldChecks.ts` — `computeCrossFieldChecks(scalars, lineItemRows)`: the deferred cross-field reconciliation logic, returning per-field and per-row check results.
- `api/src/extract/run.ts` — restructured from a single pass (compute-and-insert-immediately per field) to two passes: pass 1 computes every field's majority value + validator status without touching the DB; a cross-field pass reconciles totals and line-item math using every field's pass-1 result at once; pass 2 scores and inserts. `validateField` kept as a thin wrapper over `validateValue` (existing tests/signature unchanged); `normalizeValue` now calls `stripMoneySymbols` instead of duplicating the regex.
- `api/test/confidence/{validate,score,crossFieldChecks}.test.ts` (35 tests) — new, pure-function coverage.
- `api/test/extract/run.test.ts` — extended the shared fixture with `vendor_name`/`subtotal`/`tax`/`total` fields and full line-item columns (`quantity`/`unit_price`/`amount`, not just `description`); added tests for a required-missing field (confidence forced to 0), a reconciling vs. mismatched total (auto_accepted vs needs_review), and three new row-level tests (reconciling row → auto_accepted, arithmetic mismatch → needs_review at 0.5 confidence, invalid cell → confidence forced to 0).

### Decisions
- **Built via a Workflow: one agent implemented against a fully-specified formula (not left to invent one), two independent agents reviewed in parallel** — a general code reviewer, and a second agent whose only job was to hand-trace 7 concrete scenarios (reconciling/mismatched totals, required-vs-optional missing fields, invalid dates, row arithmetic, a no-tax doc type) through the actual code and compare against expected answers I specified up front. Both passed; findings below were folded in before commit.
- **The scoring formula** (`computeConfidence`): `validatorStatus: 'invalid'` → confidence is always `0`, unconditionally — no amount of sample agreement can rescue a value we already know is malformed (verified directly: even 3/3 samples agreeing on an unparseable date string still scores `0`). `validatorStatus: 'missing'` → `0` if the field is `required`, else `sampleAgreement` (unanimous agreement that an *optional* field is legitimately absent, e.g. an unsigned PO's `approved_by`, is real signal, not a defect). Otherwise → `sampleAgreement * 0.5 ^ (number of failed cross-field checks)` — each unreconciled cross-field check halves confidence rather than zeroing it, since a value can still be individually correct even when a related total doesn't add up (unlike a format failure, which is already known-bad).
- **Cross-field checks are "skip if not evaluable," never "fail by default."** If subtotal/tax/total aren't all individually `validatorStatus: 'valid'` first, no totals check is recorded at all for any of them — this avoids double-penalizing a value that's already being penalized for its own format failure. Same rule for the line-item sum and per-row arithmetic checks. Money comparisons use a $0.01 tolerance to absorb float rounding, not as a business "close enough."
- **Doc-type dispatch for the totals check (subtotal+tax=total vs subtotal=total) is inferred from data, not passed in.** Whether a `'tax'` key exists at all in the field-value map (invoice/receipt have one; `purchase_order` doesn't, per `scripts/fieldSpecs.ts`) already discriminates the two cases; an earlier draft threaded `docType` through as an explicit parameter, but nothing in the function actually branched on it once written — the general-review pass flagged it as dead API surface, and it was removed rather than kept as unused-but-documented.
- **Line items get real per-row validation for the first time.** Each row's own `validatorStatus` is now aggregated from validating every column's cell (`validateValue` per `column.type`) — any format-invalid cell taints the whole row (a line item can't be "mostly right"); a missing *optional* column doesn't. Combined with the new `quantity × unit_price = amount` per-row check, a line item with internally-inconsistent math or a garbage cell now actually routes to `needs_review` instead of silently inheriting whatever confidence the *other* rows in the same table happened to get.
- **A known, documented limitation:** every row in a table field still shares the *same* `sampleAgreement` value (the whole array is one unit for majority-voting purposes, per Phase 3's `pickMajority` — unchanged this phase). Per-row confidence now genuinely differs where a row's own validity or arithmetic differs, but agreement itself isn't yet computed per-row. Not fixed here — would require row-level (not whole-array) self-consistency voting, a larger change than this phase's scope.
- **A known, unreached edge case:** `decideStatus(confidence, autoAcceptThreshold)` is a plain `confidence >= threshold` comparison, so a hypothetical `autoAcceptThreshold: 0` would auto-accept even a confidence-`0` (known-invalid or missing-required) field. No field in `scripts/fieldSpecs.ts` is configured below `0.9`, so this doesn't manifest today; flagged by the conformance-review pass and left as-is rather than adding a guard against a configuration that doesn't exist, per the project's general rule against validating unreachable scenarios.

## Phase 5 — Review

### Summary
A human review queue, end to end: a backend API (queue query, accept/correct actions, review-session tracking, a page-image proxy) and the actual frontend UI — `web/src/App.tsx`, `DocViewer`, `ReviewPane` had been Phase 0 placeholders (`.gitkeep`s, and `App.tsx` literally read "review UI starts in Phase 5") until now. A reviewer works through one `needs_review` item at a time — either a scalar field or a table field with a flagged row — sees the document page image alongside the field's confidence/validator/cross-field-check context, and either accepts it as extracted or corrects it, with every resolution (including a plain accept) written to `corrections` for audit. Built and reviewed as two sequential passes (backend, then frontend against the verified backend contract), each via implement-then-independently-review.

### Files created/touched
- `api/src/review/queue.ts` — `getNextReviewItem(batchId?)`: the lowest-confidence outstanding candidate (a `needs_review` field, or a table field with a `needs_review` row underneath it even if the field's own status is `auto_accepted`), filtered to each document's *current* extraction only (see Decisions), assembled with page/column/label context for rendering.
- `api/src/review/actions.ts` — `acceptField`/`correctField`/`acceptRow`/`correctRow`, `startReviewSession`/`endReviewSession`.
- `api/src/routes/review.ts` — `POST /review-sessions[/:id/end]`, `GET /review/next`, `POST /review/fields/:id/{accept,correct}`, `POST /review/rows/:id/{accept,correct}`.
- `api/src/routes/pages.ts` — `GET /pages/:id/image`, proxying a page PNG out of private Storage.
- `api/test/review/{queue,actions}.test.ts`, `api/test/review.route.test.ts` (39 tests).
- `web/vite.config.ts` — dev-server proxy (`/api` → `localhost:3000`).
- `web/src/App.tsx` (full rewrite), `web/src/api.ts`, `web/src/types.ts`, `web/src/components/DocViewer/DocViewer.tsx`, `web/src/components/ReviewPane/{ReviewPane,RowTable,Badges}.tsx`.

### Decisions
- **Zero new dependencies, on either side.** No `@fastify/cors` — a Vite dev-server proxy makes every frontend request same-origin instead. No router, no data-fetching/state library, no hotkey library — this is one continuous view (name gate → review loop), and React's built-in hooks + native `fetch`/`keydown` are enough. Avoids re-litigating the "ask before adding dependencies outside the approved stack" rule entirely, since nothing needed to be asked.
- **The `corrections` table is the general-purpose human-review audit log, not just an edit log.** Every resolution — accept-as-is or an actual edit — writes a `corrections` row, with `oldValue`/`newValue` identical for a plain accept. This is *required*, not just tidy: `field_value_rows` has no `reviewedBy`/`reviewedAt` columns of its own (only `field_values` does), so `corrections.correctedBy`/`correctedAt` is the *only* audit trail a row-level accept has.
- **Stale-extraction exclusion is the single most important correctness property in `queue.ts`.** A document can have multiple `extractions` rows over time (re-running extraction — which happened repeatedly during Phase 3/4 development — inserts a new one each run), and an older, superseded extraction's `field_values` can sit at `status: 'needs_review'` forever if nothing resolves it. The queue resolves each candidate document's true-latest extraction (by `startedAt`) and discards any candidate whose `extractionId` doesn't match, even though the stale row's own `status` column still says `needs_review`. Independently traced against a real two-extraction scenario before commit — correct.
- **A table field and its rows are scored and reviewed independently.** `getNextReviewItem`'s inclusion condition is `field.status = 'needs_review' OR EXISTS a row with status = 'needs_review'` — a table can be `auto_accepted` at the field level (its own reconciliation checks passed) while one specific row still needs a human look, and vice versa isn't assumed either. `acceptField` on a table bulk-resolves any of its own outstanding rows (the whole table is shown when reviewing the field, so accepting it means the reviewer looked at everything on screen); `acceptRow` deliberately never touches the parent `field_values` row.
- **Ordering is `confidence ASC`, a documented v1 simplification.** A table field whose own confidence is high but which has one severely-bad row isn't prioritized by that row's severity — it still surfaces, just not with optimal urgency. Not fixed here; would need a computed sort beyond what this phase's scope justified.
- **Session counters are an atomic SQL increment** (`sql\`column + delta\``), not read-then-write — a double-fired keypress or two tabs against the same session must not silently lose one side's count. A `reviewSessionId` that doesn't exist is validated *before* any field/row mutation and fails the whole request (`404 review_session_not_found`), rather than silently dropping just the count while the review action itself still succeeds.
- **No bbox/highlight overlay on the document image.** `field_values.pageNumber`/`bbox` are never populated by this pipeline (a known gap since Phase 3/4) — `DocViewer` shows the page image plainly rather than fabricating a highlight box from data that doesn't exist.
- **The one global keyboard shortcut**: `Enter`, when nothing is focused (`document.activeElement === document.body`), accepts the current field as-is. This is the actual "keyboard-fast" loop the README describes — glance, Enter, next — without risking a global hotkey hijacking normal typing inside a correction input (every input stops Enter's propagation).

## Phase 6 — Export

### Summary
A CSV export of a batch's field values, backed by the `exports` table that's existed since Phase 1 (`target`/`status`/`rowCount`/`filePath`/`idempotencyKey` were all defined then but unused until now). `POST /batches/:id/export` builds one CSV row per document (scalar fields as columns, the table field's rows as a JSON-encoded column), uploads it to Storage, and records the export; `GET /exports/:id` polls status; `GET /exports/:id/download` streams the file back.

### Files created/touched
- `api/src/export/csv.ts` — `buildCsv(headers, rows)`: a small hand-rolled RFC 4180 serializer (quote-if-needed, double internal quotes) — no new dependency for something this size.
- `api/src/export/build.ts` — `buildBatchExportCsv(batchId, includeUnresolved)`: gathers each document's *current* extraction (same latest-extraction-only rule as Phase 5's queue — re-running extraction must not export stale data either), decides per-field whether it's resolved, and produces the CSV text.
- `api/src/routes/exports.ts` — `POST /batches/:id/export`, `GET /exports/:id`, `GET /exports/:id/download`.
- `api/test/export/{csv,build}.test.ts`, `api/test/exports.route.test.ts` (20 tests).

### Decisions
- **Unresolved fields are blanked by default, not exported as if final.** `buildBatchExportCsv` only uses a field's value when its status is `auto_accepted`/`confirmed`/`corrected` (`finalValue ?? normalizedValue` — `finalValue` is only ever set by a Phase 5 review action, so this correctly falls back to the model's own value for the common auto-accepted case). A `needs_review` field's cell is left empty unless the caller explicitly passes `includeUnresolved: true`. This is the same principle Phase 5 was built around: don't present unverified data as if it were verified. Each document row also carries `resolved_field_count`/`total_field_count` (scalar fields only) so a consumer can see completeness at a glance without parsing every column.
- **Table fields are serialized as one JSON column, not a second file.** `exports.filePath` is a single column — a wide CSV with the line-items table JSON-encoded per document (`[{rowIndex, status, cells}]`, same resolved-vs-blanked rule applied per row) is simpler than a two-file/zip scheme and still fully machine-readable. A normalized long-format export (one row per document×line-item) is a plausible future enhancement, not built here.
- **`idempotencyKey` is caller-supplied and genuinely idempotent**, not just a dedupe check — retrying a `POST` with the same key returns whatever export already exists (whatever its current status), rather than a 409 conflict. This is a deliberate departure from `schemas.ts`'s 409-on-duplicate convention: a schema name+version colliding is a real naming conflict, but an idempotency key colliding is the caller retrying the same logical request, which should succeed with the original result. The key is claimed via the `exports` insert itself (not a pre-check-then-insert), so two concurrent requests with the same key can't both proceed — the unique constraint is the actual source of truth.
- **A missing/bad `batchId` returns a clean `400 unknown_batch_id`** (caught via `isForeignKeyViolation` on the `exports.batch_id` FK, same convention as `batches.ts`'s `schemaId` and Phase 5's `review-sessions.batchId`), not a bare 500.
- **The Supabase bucket's `allowed_mime_types` needed a real change.** `erp-documents` was provisioned in Phase 0 with only `application/pdf`/`image/png`/`image/jpeg` allowed — a CSV upload would have been rejected by Storage, and none of the existing allowed types were an honest fit. Confirmed with the user before making the change (a live edit to shared infrastructure, even though low-risk and strictly additive); added `text/csv` via the same `supabase_execute_sql` approach Phase 0 used to create the bucket, verified before and after — `public`, `file_size_limit`, and the three original MIME types are unchanged.
- **No CI-style implement/review Workflow this phase** (ultracode was off) — built and self-reviewed directly, including a live sandbox route-registration/validation check (`POST`/`GET` against the running server) the same way every prior phase's sandbox-reachable checks have been done.

## Phase 7 — Eval

### Summary
A gold-set eval harness: `scripts/run-eval.ts` compares every dev-subset document's current (post-review) extraction against `samples/manifest.json`'s ground truth (present since Phase 1 — the synthetic generator always emitted the true field/line-item values it rendered onto each PDF, specifically for this purpose) and reports the project's headline metric — **auto-accept precision**: of the fields the system decided *not* to send to a human, what fraction were actually right.

### Files created
- `api/src/eval/goldSet.ts` — loads and indexes `samples/manifest.json` by filename.
- `api/src/eval/compare.ts` — `valuesMatch(type, extracted, gold)`: per-field-type comparison (money/number compared numerically after stripping symbols; date compared by calendar day via `Date.parse`, not raw string, so "Sep 19, 2025" and "2025-09-19" agree; string/enum trimmed exact match). `compareLineItems(extractedRows, goldRows)`: positional row comparison for the `line_items` table field.
- `api/src/eval/run.ts` — `runEval()`: for each `documents.inDevSubset = true` document (the DB column, not the manifest's own copy of the flag — the DB is the authority on what's actually been extracted), resolves its latest extraction (same stale-extraction guard as Phase 5/6: `orderBy(desc(extractions.startedAt)).limit(1)`, scoped per document), compares every field, and aggregates `autoAcceptPrecision` / `overallAccuracy` / `automationRate`, each computed overall and broken down `byDocType`/`byDifficultyGroup`.
- `scripts/run-eval.ts` — CLI entry point (`npx tsx scripts/run-eval.ts`): prints a report, lists every mismatch, writes full detail to `eval-results.json` (gitignored — a report of current DB state, not source truth).
- Tests: `api/test/eval/{compare,run}.test.ts` (23 tests).

### A critical bug found by independent review, before this was committed
Given this metric is the project's one-line pitch, an independent review agent was asked to adversarially trace the logic before commit (same bar as Phase 4/5's implement-then-review pattern) — it found, and empirically reproduced, a real inflation bug: **a table field's own `status` can stay `auto_accepted` forever even after a human corrects one of its individual rows.** `review/actions.ts`'s row-level `acceptRow`/`correctRow` set that row's `finalCells` but deliberately never touch the parent `field_values.status` (this is intentional, UI-supported behavior — `ReviewPane.tsx` literally renders "*this field is already auto accepted — only its rows below still need review*"). The first version of `run.ts` computed a table field's `matched` using `finalCells ?? cells` (correct for `overallAccuracy`) but then attributed that match to `status: 'auto_accepted'` for auto-accept-precision purposes too — silently crediting the human's fix as "the model got this right unsupervised." Reproduced directly: a table field with a wrong raw value, one row human-corrected to match gold, `status` still `auto_accepted` → reported 100% auto-accept precision on a field the model actually got wrong.

**Fix:** added `countsAsAutoAccept` to each field's eval result — true for a scalar field iff `status === 'auto_accepted'` (unchanged; `finalValue` is guaranteed null in that state, so no divergence is possible), true for a table field iff `status === 'auto_accepted'` **and** no row has a non-null `finalCells`. Both `autoAcceptPrecision` and `automationRate` now gate on this instead of raw `status`. `api/test/eval/run.test.ts` has a dedicated regression test reproducing the exact scenario the review found, asserting the field is now excluded from both the numerator and denominator (not wrongly counted as a match, and not silently miscounted as "no data" either).

Two smaller findings from the same review were also fixed: `compare.ts`'s money/number parsing didn't guard against `Number('')`/`Number('  ')` coercing to `0` (the exact gotcha `confidence/validate.ts` already guards against explicitly) — a blank or junk extracted value could have silently matched a genuine gold value of `"0"`; not currently reachable (no field in this 60-doc corpus has a gold value of zero), but fixed anyway since the guard is cheap and directly analogous to an existing one. A third finding — `Date.parse` treats an ISO date string as UTC midnight but a verbose one as local midnight, a theoretical one-day drift on a host with a large positive UTC offset — was left **not fixed**, documented inline in `compare.ts`: this deployment runs UTC and the corpus only ever prints ISO dates on the page (`fmtDateISO`, not the unused `fmtDateDisplay`), so the condition can't currently occur.

### An honest limitation of this metric, worth stating plainly
Auto-accept precision measures **value correctness against gold**, not **presentation anomalies**. The deferred currency-mismatch case from the Phase 6 checkpoint (`receipt_edge_case_02.pdf`, a line item printed in `€` on an otherwise-USD receipt) has a gold `amount` of `"7.62"` — a plain number, no symbol — because the generator's ground truth was always the numeric value regardless of which symbol got rendered. `stripMoneySymbols` strips `€` exactly as it strips `$`, so that field's raw value numerically matches gold, and **this eval will not flag it as a miss**, even though a human reviewer would likely still want to see a currency symbol that doesn't match the rest of the document. This isn't a bug in this phase — the eval is correctly measuring what it's defined to measure — but it means "the eval reports high precision" is not by itself proof that every anomaly a careful human would catch has been caught. Recorded here so this doesn't read as a contradiction later.

## Phase 9 — CI (new work, user-directed)

### Summary
Every PR through this whole project (9 of them) merged on `mergeable_state: clean` alone — no conflicts — with nothing automatically running the test suite or typecheck first. `.github/workflows/ci.yml` closes that: a GitHub Actions workflow running on every push to `main` and every PR targeting it.

### What it runs
`npm install` → `npm run typecheck` (all three tsconfigs: api, web, scripts) → `npm run test` (167 tests) → `npm run build` (api + web) → `npm run lint --workspace web` (oxlint).

### Decisions
- **Node 20, not whatever's locally available.** `package.json`'s `engines` field declares `>=20 <21`, but this project has actually been built and run all session on Node 22 (this sandbox) and Node 24 (the user's machine) without issue — neither has ever hit the declared, supported version. CI intentionally checks the declared contract rather than mirroring whatever happened to work locally; if Node 20 ever fails here, that's a real finding (either the `engines` field is wrong, or there's a genuine Node-20-specific bug), not noise to route around.
- **No secrets configured, deliberately.** Every test file stubs `DATABASE_URL`/`SUPABASE_*`/`ANTHROPIC_API_KEY` with fake local values before importing app code, specifically so the suite runs without touching real infrastructure — the same property that's let it run identically in this fully offline sandbox all through development. `build` needs nothing at build time either (the web app talks to the API via a dev-server proxy, nothing is baked in). This means CI has zero access to real credentials, by design, not by oversight.
- **Verified locally before pushing, not just written and hoped**: ran the exact same command sequence (`typecheck`, `test`, `build`, `lint --workspace web`) directly in the sandbox first — `build` specifically had never been run end-to-end this entire session (only `typecheck`/`test` individually), and it needed to be proven to actually succeed before being wired into a required check. All four passed cleanly.
- Added a CI status badge to `README.md`, linking to the workflow.

### Checkpoint — the workflow's own first run found two real bugs

Checked rather than merged on `mergeable_state` alone (which read `unstable`, not `clean`, for the first time ever on this project — a real signal, followed up on rather than ignored): the PR's own CI run **failed**. Fetched the actual job logs rather than guessing, and both failures turned out real, not flaky:

1. **`pdfjs-dist@6.2.108` genuinely requires Node `>=22.13.0 || >=24`** and fails at runtime on Node 20 — `TypeError: buffer.transferToFixedLength is not a function` inside PDF page rendering, plus a 5-second test timeout on `pageRender.test.ts`'s multipage case. This is exactly the situation the CI decision doc anticipated ("if Node 20 ever fails here, that's a real finding") — confirmed real: `engines` was updated from `>=20 <21` to `>=22.13.0` (matching what every environment this project has actually run on already was), and CI now uses Node 22.
2. **Two test files (`test/extract/run.test.ts`, `test/ingest/hash.test.ts`) had zero env-var stubbing** and had only ever passed by accident — riding on Vitest sharing a worker thread with some other file that happened to set the stubs first, an ordering this sandbox and the user's machine both happened to get "right" but GitHub's runner didn't. Verified precisely (not guessed) by temporarily hiding this sandbox's own `.env` file (which was masking the same risk locally — `dotenv` reads it regardless of what's `unset` in the shell) and running each of the 13 test files lacking the stub pattern individually; exactly these 2 failed, matching CI exactly. `run.test.ts` got the standard stub block (its `env.js`-importing dependency is loaded via a non-hoisted dynamic `import()`, so ordering the stub before it works); `hash.test.ts` needed its static `import` converted to a dynamic one too, since a static import is hoisted and would load `env.js` before any stub could run regardless of textual position.

Re-verified the full sequence (`typecheck`/`test`/`build`/`lint`) locally with `.env` removed entirely both times — 167/167 pass with zero real credentials present, matching CI's actual conditions exactly, not just "works on this machine."

## Phase 10 — Deployment (new work, user-directed)

### Summary
First real deployment: `/api` is now live on Railway with a public URL, as its own dedicated service **`API-ERP`** alongside `Postgres-ERP` in "Upwork Portfolio". Since this is the first time the API has ever been reachable from outside a local machine or this sandbox, a shared-secret auth gate went in first — everything up through Phase 9 assumed an unauthenticated local API. `/web` was deliberately **not** deployed in this pass (user chose "API only" as the first step over deploying both); the review UI still runs locally, now optionally pointed at the deployed API instead of a local one.

### What was built
- **`api/src/lib/auth.ts`** (`registerAuthGate`) — a single `onRequest` hook checked against `env.API_SHARED_SECRET` via `crypto.timingSafeEqual` (constant-time, to avoid a timing side-channel on the comparison), required as an `x-api-key` header. `/health` is explicitly exempt (path-checked before the secret check) because Railway's own platform healthcheck can't send custom headers.
- **`API_SHARED_SECRET` added to `EnvSchema` as *optional***, not required — deliberately, so the gate is a no-op (and logs a boot-time warning) when unset. This is what keeps local dev and all 172 existing tests running exactly as before, unauthenticated, with zero test-file changes; the gate only activates where it's actually configured (Railway).
- **`api/test/lib/auth.test.ts`** (5 tests, isolated Fastify instance, doesn't go through `buildApp()`/DB mocking) — unset secret is a no-op; set secret rejects no header and a wrong header with 401; correct header passes through; `/health` is reachable with no header even when a secret is configured.
- **`web/vite.config.ts`** — the dev proxy target and an optional injected `x-api-key` header are now read server-side via Vite's `loadEnv` from `web/.env.local` (gitignored, documented in the new `web/.env.example`) as `API_PROXY_TARGET`/`API_SHARED_SECRET`. Deliberately **not** `VITE_`-prefixed — a `VITE_` prefix gets inlined into the client bundle by Vite, which would ship the shared secret to anyone opening devtools. Read this way, the secret only ever lives in the Node dev-server process. Omitting both env vars reproduces today's exact behavior (proxy to `localhost:3000`, no header).

### Infrastructure provisioned
- **Railway service `API-ERP`** (id `ac1b4b79-a748-49c9-8b3e-ca1d8e80a81b`) in "Upwork Portfolio" (project `f5549c0c-4269-4f60-a1dd-f12e6543ffc8`, env `production` `6be5b32b-e74e-4d9a-b027-bc406b715688`), source `NovaVey/Extraction-Review-Pipeline` branch `claude/extraction-review-pipeline-5e3oro` (the only branch with any real code — `main` is still the original empty scaffold commit, confirmed via `git rev-list main...claude/extraction-review-pipeline-5e3oro` showing 0 commits ahead on `main`, 40 on this branch).
- Service instance configured via Railway's GraphQL API (`serviceInstanceUpdate`, introspected `ServiceInstanceUpdateInput` first rather than guessing field names): `rootDirectory` left at the repo root (required for npm workspaces to resolve correctly — `api/`'s deps are hoisted to the root `node_modules`), `buildCommand: npm run build --workspace api`, `startCommand: npm run start --workspace api`, `healthcheckPath: /health`, `healthcheckTimeout: 30`.
- Public domain: **`api-erp-production-dfd8.up.railway.app`**.
- Env vars set on the service: same real values as local `.env` for `SUPABASE_URL`/`SUPABASE_SERVICE_KEY`/`STORAGE_BUCKET`/`ANTHROPIC_API_KEY`/`EXTRACTION_MODEL`/`EXTRACTION_TEMPERATURE`/`SAMPLE_COUNT`/`SUBSET_SIZE`/`RETENTION_DAYS`, plus a freshly generated `API_SHARED_SECRET` (32 random bytes, hex-encoded, via Node's `crypto.randomBytes` — not reused from anywhere). One deliberate difference from local: **`DATABASE_URL` is the Railway variable reference `${{Postgres-ERP.DATABASE_URL}}`** (resolves to the private `postgres-erp.railway.internal` address), not the `DATABASE_PUBLIC_URL` proxy value local dev uses — `API-ERP` runs inside the same Railway project as `Postgres-ERP`, so it can and should reach it over the private network instead of round-tripping through the public TCP proxy. Using a reference instead of a copied literal also means it stays correct automatically if `Postgres-ERP`'s connection info ever changes.
- `PORT` needed no explicit configuration — Railway injects it automatically (confirmed in runtime logs: `Server listening at http://127.0.0.1:8080`), and `env.ts`'s existing `PORT` schema (already used for local dev) picks it up with no code change.

### Decisions
- **A new dedicated service, not the existing `Document-Extractor-Worker`/`Document-Extractor-Web` services already sitting in "Upwork Portfolio".** Neither is mentioned anywhere in this project's own history, and the project hosts several other unrelated portfolio pieces (`Invoice-Generator`, `Booking-Reminder-System`, `Client-CRM-Dashboard`, `Lead-Intake-Pipeline`, `AI-Reply-Assistant`, `Subscription-Billing-Kit`) — confirmed with the user before creating anything: those two are an unrelated, similarly-themed portfolio project, not this one. `API-ERP` follows the same dedicated-service, shared-project isolation precedent `Postgres-ERP` already established in Phase 0.
- **Auth gate is fail-open only when unconfigured, fail-closed once a secret is set** — not required-with-no-default. The alternative (required, no default) would have meant editing the env stub block in 8 existing test files for a concern (public exposure) that doesn't apply to any of them. The accepted risk is a deploy that forgets to set the secret would be silently unauthenticated; mitigated with an unconditional boot-time warning log (`API_SHARED_SECRET not set — all routes are unauthenticated`) rather than adding a new environment-mode concept (`NODE_ENV`-gated behavior) this codebase has no other precedent for.
- **`x-api-key` header, not `Authorization: Bearer`** — this is a single shared secret gating an internal deployment, not per-user auth; `x-api-key` reads unambiguously as that and doesn't imply a token scheme (JWT, OAuth) that isn't actually in use.
- **Scope: API only, deploying `/web` deferred.** Chosen over deploying both, so the first production exposure of this codebase is one smaller, easier-to-verify surface (an API that until now has only ever been hit locally or via `.inject()` in tests) rather than two at once.
