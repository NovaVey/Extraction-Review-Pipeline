## Phase 2 — Ingest

### Summary
PDF ingest pipeline (page rasterization, text-layer extraction, OCR fallback, sha256 hash-dedupe, Supabase Storage upload, `documents`/`pages` row writes), the `POST /schemas`, `POST /batches`, `GET /batches/:id`, and `POST /batches/:id/documents` routes, and two operator scripts to seed the three doc-type schemas and bulk-ingest the full 60-doc corpus.

### Files created/touched
- `api/src/ingest/pageRender.ts` — rasterizes each PDF page to a PNG via `pdfjs-dist` + `@napi-rs/canvas` (`RENDER_SCALE = 2.0`, ~144 DPI equivalent).
- `api/src/ingest/textLayer.ts` — per-page embedded-text extraction via `pdfjs-dist`; `hasTextLayer` is true once a page has ≥5 extracted characters.
- `api/src/ingest/ocr.ts` — `tesseract.js` OCR fallback for pages without a usable text layer; shares one worker across a whole ingest run.
- `api/src/ingest/upload.ts` — `ingestDocument()`: sha256-hash the upload, short-circuit on an existing `(batchId, sha256)` row, else upload the original PDF + each page's PNG to Storage, insert `documents`/`pages` rows, and mark the document `processed` (or `failed` with `failureReason` if any step throws).
- `api/src/lib/storage.ts` — added `uploadObject()` (content-addressed `POST .../object/{bucket}/{path}` with `x-upsert: true`) alongside the existing Phase 0 `pingStorage()`.
- `api/src/lib/pgErrors.ts` — `isUniqueViolation` / `isForeignKeyViolation` helpers (matches node-postgres's SQLSTATE `.code`), used to turn constraint violations into clean 409/400 responses instead of raw 500s.
- `api/src/routes/schemas.ts` — `POST /schemas` (Zod-validated `FieldSpec[]` body, 409 on duplicate name+version).
- `api/src/routes/batches.ts` — `POST /batches` (400 on unknown `schemaId`), `GET /batches/:id` (batch + its documents, 404 if missing), `POST /batches/:id/documents` (multipart, one or more PDFs, per-file success/error results; only `application/pdf` accepted since page images are derived, never uploaded directly).
- `api/src/app.ts` — registered `@fastify/multipart` (20MB file size cap, matching the Storage bucket's own limit) and the two new route plugins.
- `scripts/seed-schemas.ts` — inserts one v1 `extraction_schemas` row per doc type from `fieldSpecs.ts`; safe to re-run (skips an existing name+version).
- `scripts/ingest-corpus.ts` — reads `samples/manifest.json`, creates (or reuses) one batch per doc type, ingests all 60 documents via `ingestDocument()`, carrying each document's `inDevSubset` flag over from the manifest verbatim rather than re-deciding it. Idempotent re-run (batches reused by name+schema, documents deduped by sha256 inside `ingestDocument`); prints a final ingested/deduped/failed summary and exits non-zero if anything failed.
- `api/test/fixtures.ts`, `api/test/ingest/{hash,textLayer,pageRender,ocr,upload}.test.ts` — see Testing below.
- `api/package.json` — added `@fastify/multipart`, `pdfjs-dist`, `tesseract.js`, `@tesseract.js-data/eng`; `@napi-rs/canvas` bumped `^0.1.65` → `^1.0.0`.
- `api/tsconfig.json` — added `"lib": ["ES2022"]`.
- `package.json` (root) — added `"type": "module"`; `typecheck` script now also runs `scripts/tsconfig.json`.
- `scripts/tsconfig.json` (new) — gives `/scripts` the same real `tsc --noEmit` coverage as `api`/`web`.
- `.gitignore` — added `*.traineddata`.

### Decisions
- **`@napi-rs/canvas` bumped `^0.1.65` → `^1.0.0`.** `pdfjs-dist` v6's renderer calls `ctx.fill(path)` with a `Path2D` argument; 0.1.x's Canvas 2D implementation doesn't support that overload (`"Value is none of these types String, Path"`). Re-verified against both new (`pageRender.ts`) and existing (Phase 1's `make-synthetic-docs.ts`) consumers after the bump — no regressions.
- **OCR trained-data: added `@tesseract.js-data/eng` as a pinned dependency, rather than tesseract.js's CDN default.** tesseract.js normally fetches English trained data from `cdn.jsdelivr.net` at runtime, which this sandbox's egress policy blocks (`403`, same class of restriction as Supabase/Railway in Phase 0). `@tesseract.js-data/eng` ships the identical file as a plain npm package (`registry.npmjs.org` — already reachable, same host `npm install` itself uses); pointing `createWorker`'s `langPath` at its local `node_modules` path removes the CDN dependency entirely, in this sandbox **and** in production (no more runtime reliance on jsdelivr's uptime). Confirmed via `AskUserQuestion` before adding — a new dependency outside the originally-approved stack list. Also set `cacheMethod: 'none'`: without it, tesseract.js additionally writes a *decompressed* copy of the trained-data file into the current working directory on first use, which briefly left a stray untracked `eng.traineddata` (~5MB) at the repo root during testing; since `langPath` already reads instantly from a local, permanent path, that cache added no value and is now suppressed at the source. The stray file itself was deleted (never committed) and `*.traineddata` added to `.gitignore` defensively.
- **`api/tsconfig.json` root cause fix, not a workaround: `"lib": ["ES2022"]`.** `uploadObject()`'s `fetch(url, { body: someBuffer })` failed to typecheck with confusing "Buffer not assignable to BodyInit... missing URLSearchParams properties" errors. Root cause: neither `api/tsconfig.json` nor the shared `tsconfig.base.json` set `lib` explicitly, so TypeScript's target-based default (`ES2022` → implicitly `DOM` + `DOM.Iterable` too) pulled in `lib.dom.d.ts`'s own `fetch`/`BodyInit` globals alongside `@types/node`'s, and the two competing declarations didn't structurally agree on typed-array bodies. `/api` is pure backend code with no browser surface, so scoping it to `lib: ["ES2022"]` (no DOM) removes the phantom second declaration entirely — `/web`'s own independent tsconfig (Vite's standard split config) still has DOM and is untouched.
- **Root `package.json` root cause fix: added `"type": "module"`.** Every script under `/scripts` uses `import.meta.url` (ESM-only), but the root `package.json` never declared `"type": "module"` — under `moduleResolution: NodeNext`, that makes TypeScript treat root-level `.ts` files as CommonJS-intended by default (`tsc` even flagged it explicitly once `/scripts` got real typecheck coverage: `import.meta not allowed in CommonJS output`). `tsx`'s runtime loader is permissive enough that this never surfaced as a runtime failure (Phase 1's `make-synthetic-docs.ts` ran fine despite it), but it's a real latent inconsistency, not just a new-script problem — fixed at the root rather than worked around per-file.
- **`scripts/tsconfig.json` added**, extending the shared base, `include: ["**/*.ts"]`, wired into the root `typecheck` script. Justified now (wasn't in Phase 1) because `seed-schemas.ts`/`ingest-corpus.ts` are the first root-level scripts to import across the `/scripts` ↔ `api/src` boundary — exactly the boundary the `"type": "module"` bug above was hiding in.
- **Storage upload stays on plain `fetch`, no `@supabase/supabase-js`** — continues the Phase 0 decision; `uploadObject()` is one more REST call in the same style as `pingStorage()`.
- **Storage path convention:** `batches/{batchId}/{sha256}/original.pdf` and `batches/{batchId}/{sha256}/pages/{pageNumber}.png` — content-addressed by sha256 *within* a batch (scoped per-batch, not globally, so one batch's later retention purge can't delete another batch's copy of the same bytes) and upserted (`x-upsert: true`), so retrying a partially-failed ingest is always safe.
- **`documents.hasTextLayer` = true only if *every* page has a text layer; `documents.ocrRequired` = true if *any* page doesn't.** Matches how this was already verified against the corpus in this session (`hasTextLayer` cross-checked 0 mismatches against `manifest.json`'s `difficultyGroup !== 'scanned'`, which is itself a whole-document label).
- **Known limitation, not fixed this phase:** text-layer detection is whole-page, not per-field. The "handwriting-in-one-field" edge-case docs (Phase 1) embed only *one* field as a rasterized image inside an otherwise normal text PDF — the page's other fields keep `hasTextLayer` comfortably above the 5-character threshold, so OCR fallback never triggers for that page, and that one field's value is only recoverable from the page image, not from `pages.textContent`. Extraction (Phase 3+) will need to reason from the rendered page image for cases like this regardless of the page-level flag; flagging here so it isn't mistaken for a bug later.
- **`/samples` corpus was regenerated once during this phase** (`npm run gen:samples`), while verifying the `@napi-rs/canvas` bump didn't break Phase 1's generator — same composition (60 docs, 20/20/20 by doc type, 15/15/15/15 by difficulty group, 10 in the dev subset), fresh `Math.random()`-fabricated field values throughout. The generator's own design treats this as expected/harmless (its header comment notes `Math.random()` is deliberately unseeded, "this is a one-shot local script"), and every Phase 2 test in this session runs against the current on-disk corpus successfully — committing the regenerated files rather than reverting to Phase 1's original random draw.
- **`POST /batches/:id/documents` only accepts `application/pdf`** — page images are always derived from the uploaded PDF by this pipeline, never uploaded directly, so accepting image mimetypes here would be misleading.
- **`scripts/ingest-corpus.ts` groups the corpus into one batch per doc type** (`"invoice corpus"`, `"receipt corpus"`, `"purchase_order corpus"`), matching the schema-per-batch relationship (`batches.schemaId` is a single FK) and the fact each doc type has its own schema from `seed-schemas.ts`.
