## Phase 2 — Ingest

### Summary
PDF ingest pipeline (page rasterization, text-layer extraction, OCR fallback, sha256 hash-dedupe, Supabase Storage upload, `documents`/`pages` row writes), the `POST /schemas`, `POST /batches`, `GET /batches/:id`, and `POST /batches/:id/documents` routes, and two operator scripts to seed the three doc-type schemas and bulk-ingest the full 60-doc corpus.

### Files created/touched

- `api/src/ingest/textLayer.ts` — per-page embedded-text extraction via `pdfjs-dist`; `hasTextLayer` is true once a page has ≥5 extracted characters.
- `api/src/ingest/ocr.ts` — `tesseract.js` OCR fallback for pages without a usable text layer; shares one worker across a whole ingest run.
- `api/src/ingest/upload.ts` — `ingestDocument()`: sha256-hash the upload, short-circuit on an existing `(batchId, sha256)` row, else upload the original PDF + each page's PNG to Storage, insert `documents`/`pages` rows, and mark the document `processed` (or `failed` with `failureReason` if any step throws).

### Decisions
- **`@napi-rs/canvas` bumped `^0.1.65` → `^1.0.0`.** `pdfjs-dist` v6's renderer calls `ctx.fill(path)` with a `Path2D` argument; 0.1.x's Canvas 2D implementation doesn't support that overload (`"Value is none of these types String, Path"`). Re-verified against both new (`pageRender.ts`) and existing (Phase 1's `make-synthetic-docs.ts`) consumers after the bump — no regressions.
- **OCR trained-data: added `@tesseract.js-data/eng` as a pinned dependency, rather than tesseract.js's CDN default.** tesseract.js normally fetches English trained data from `cdn.jsdelivr.net` at runtime, which this sandbox's egress policy blocks (`403`, same class of restriction as Supabase/Railway in Phase 0). `@tesseract.js-data/eng` ships the identical file as a plain npm package (`registry.npmjs.org` — already reachable, same host `npm install` itself uses); pointing `createWorker`'s `langPath` at its local `node_modules` path removes the CDN dependency entirely, in this sandbox **and** in production (no more runtime reliance on jsdelivr's uptime). Confirmed via `AskUserQuestion` before adding — a new dependency outside the originally-approved stack list. Also set `cacheMethod: 'none'`: without it, tesseract.js additionally writes a *decompressed* copy of the trained-data file into the current working directory on first use, which briefly left a stray untracked `eng.traineddata` (~5MB) at the repo root during testing; since `langPath` already reads instantly from a local, permanent path, that cache added no value and is now suppressed at the source. The stray file itself was deleted (never committed) and `*.traineddata` added to `.gitignore` defensively.
- **`api/tsconfig.json` root cause fix, not a workaround: `"lib": ["ES2022"]`.** `uploadObject()`'s `fetch(url, { body: someBuffer })` failed to typecheck with confusing "Buffer not assignable to BodyInit... missing URLSearchParams properties" errors. Root cause: neither `api/tsconfig.json` nor the shared `tsconfig.base.json` set `lib` explicitly, so TypeScript's target-based default (`ES2022` → implicitly `DOM` + `DOM.Iterable` too) pulled in `lib.dom.d.ts`'s own `fetch`/`BodyInit` globals alongside `@types/node`'s, and the two competing declarations didn't structurally agree on typed-array bodies. `/api` is pure backend code with no browser surface, so scoping it to `lib: ["ES2022"]` (no DOM) removes the phantom second declaration entirely — `/web`'s own independent tsconfig (Vite's standard split config) still has DOM and is untouched.
- **Root `package.json` root cause fix: added `"type": "module"`.** Every script under `/scripts` uses `import.meta.url` (ESM-only), but the root `package.json` never declared `"type": "module"` — under `moduleResolution: NodeNext`, that makes TypeScript treat root-level `.ts` files as CommonJS-intended by default (`tsc` even flagged it explicitly once `/scripts` got real typecheck coverage: `import.meta not allowed in CommonJS output`). `tsx`'s runtime loader is permissive enough that this never surfaced as a runtime failure (Phase 1's `make-synthetic-docs.ts` ran fine despite it), but it's a real latent inconsistency, not just a new-script problem — fixed at the root rather than worked around per-file.
- **`scripts/tsconfig.json` added**, extending the shared base, `include: ["**/*.ts"]`, wired into the root `typecheck` script. Justified now (wasn't in Phase 1) because `seed-schemas.ts`/`ingest-corpus.ts` are the first root-level scripts to import across the `/scripts` ↔ `api/src` boundary — exactly the boundary the `"type": "module"` bug above was hiding in.
- **Storage upload stays on plain `fetch`, no `@supabase/supabase-js`** — continues the Phase 0 decision; `uploadObject()` is one more REST call in the same style as `pingStorage()`.
- **Storage path convention:** `batches/{batchId}/{sha256}/original.pdf` and `batches/{batchId}/{sha256}/pages/{pageNumber}.png` — content-addressed by sha256 *within* a batch (scoped per-batch, not globally, so one batch's later retention purge can't delete another batch's copy of the same bytes) and upserted (`x-upsert: true`), so retrying a partially-failed ingest is always safe.
- **`documents.hasTextLayer` = true only if *every* page has a text layer; `documents.ocrRequired` = true if *any* page doesn't.** Matches how this was already verified against the corpus in this session (`hasTextLayer` cross-checked 0 mismatches against `manifest.json`'s `difficultyGroup !== 'scanned'`, which is itself a whole-document label).
- **Known limitation, not fixed this phase:** text-layer detection is whole-page, not per-field. The "handwriting-in-one-field" edge-case docs (Phase 1) embed only *one* field as a rasterized image inside an otherwise normal text PDF — the page's other fields keep `hasTextLayer` comfortably above the 5-character threshold, so OCR fallback never triggers for that page, and that one field's value is only recoverable from the page image, not from `pages.textContent`. Extraction (Phase 3+) will need to reason from the rendered page image for cases like this regardless of the page-level flag; flagging here so it isn't mistaken for a bug later.
- **`/samples` corpus was regenerated once during this phase** (`npm run gen:samples`), while verifying the `@napi-rs/canvas` bump didn't break Phase 1's generator — same composition (60 docs, 20/20/20 by doc type, 15/15/15/15 by difficulty group, 10 in the dev subset), fresh `Math.random()`-fabricated field values throughout. The generator's own design treats this as expected/harmless (its header comment notes `Math.random()` is deliberately unseeded, "this is a one-shot local script"), and every Phase 2 test in this session runs against the current on-disk corpus successfully — committing the regenerated files rather than reverting to Phase 1's original random draw.
- **`POST /batches/:id/documents` only accepts `application/pdf`** — page images are always derived from the uploaded PDF by this pipeline, never uploaded directly, so accepting image mimetypes here would be misleading.
- **`scripts/ingest-corpus.ts` groups the corpus into one batch per doc type** (`"invoice corpus"`, `"receipt corpus"`, `"purchase_order corpus"`), matching the schema-per-batch relationship (`batches.schemaId` is a single FK) and the fact each doc type has its own schema from `seed-schemas.ts`.
- **Bug found and fixed on the user's Windows machine, not visible in this sandbox: `pageRender.ts`'s `GlobalWorkerOptions.workerSrc`.** pdfjs-dist loads it via a dynamic `import()`, which needs a real URL. A raw `path.resolve()` result happens to work on POSIX (no scheme ambiguity) but fails on Windows — a drive letter like `C:\Users\...` gets misparsed as a URL scheme (`"Setting up fake worker failed: ... Received protocol 'c:'."`), and every one of the 60 documents failed on the first `ingest-corpus.ts` run as a result. Fixed by wrapping the resolved path in `pathToFileURL(...).href` (`node:url`), which is correct on every platform — not a Windows-only branch. `standardFontDataUrl` (same file) turned out not to need the same fix: it's consumed via `fs.readFile()` internally (traced through pdfjs-dist's source to confirm rather than assume), which accepts raw OS paths fine. Re-ran the full test suite in this sandbox after the fix — no regressions — then the user re-ran `ingest-corpus.ts` on Windows: `ingested=60 deduped=0 failed=0`.

## Phase 3 — Extract

### Summary
LLM-based structured extraction: one Anthropic Messages API call per sample (`SAMPLE_COUNT=3` samples per document), each given every page's extracted text *and* rendered image, constrained to a JSON Schema built from the document's `extraction_schemas.fields`. Samples are combined by self-consistency voting — the value most samples agree on is stored, and the agreement fraction becomes the field's confidence — writing `extractions`, `field_values`, and `field_value_rows` rows. Wired into `POST /documents/:id/extract` and `scripts/extract-devset.ts`. Hard-restricted to the 10-doc dev subset (`documents.inDevSubset`), enforced in code, not just by convention.

### Files created/touched
- `api/src/extract/schema.ts` — `buildExtractionJsonSchema(fields)`: maps `extraction_schemas.fields` (`FieldSpec[]`) to the JSON Schema passed as `output_config.format.schema`.
- `api/src/extract/anthropic.ts` — `extractSample()`: builds the per-page text+image content blocks, calls `client.messages.parse()` with `output_config.format` (structured output) and `thinking: {type: 'adaptive'}`, no `temperature`.
- `api/src/extract/run.ts` — `extractDocument(documentId)`: the orchestrator (DB reads, N parallel samples, majority-vote confidence, basic per-field validation, DB writes). Exports `pickMajority`/`validateField` directly for unit testing.
- `api/src/lib/storage.ts` — added `downloadObject()` (Phase 2 only had `uploadObject`/`pingStorage`) to fetch page PNGs back out of Storage for the extraction request.
- `api/src/routes/extract.ts` — `POST /documents/:id/extract`, registered in `app.ts`.
- `scripts/extract-devset.ts` — bulk-runs extraction over every `inDevSubset: true` document.
- `api/test/extract/{schema,run}.test.ts` — see Testing below.

### Decisions
- **Structured Outputs (`output_config.format`), not tool-use, for extraction.** `client.messages.parse()` validates/parses the response against the schema automatically (confirmed by reading the SDK's actual `parser.js`: for a plain `json_schema` format — not just a Zod-derived one — it falls back to `JSON.parse()` on the response text, so this works without a Zod dependency). This is the tool built for "extract into a schema," not a fit-for-purpose-but-wrong tool.
- **Nullability requires `anyOf`, not a `type` array — found via a real 400, not assumed.** The first live request with `currency: {type: ['string','null'], enum: [...]}` was rejected: `"Enum value 'USD' does not match declared type '['string', 'null']'"`. Fixed by expressing nullable fields as `{anyOf: [{type: 'string', enum: [...]}, {type: 'null'}]}` instead — every field is still marked `required` (must be present in the response), but its value can legitimately be `null` for a field genuinely absent from the document (the `missing_required_field` synthetic edge case is exactly this case, and is meant to produce a real, non-error null, not a fabricated value).
- **Every page is sent as both extracted text and a rendered image**, not one or the other. Text alone would fail outright on the 15 scanned docs and the handwriting edge case (no usable text layer, by design); images alone would waste tokens re-deriving what OCR/the text layer already got right on the other 45. The system prompt explicitly tells the model the image is ground truth when the two disagree.
- **The Phase 0 temperature question is resolved.** `claude-sonnet-5` still rejects a non-default `temperature` with a 400 (re-confirmed via the `claude-api` skill). `extractions.temperature` (`NOT NULL`) stores the *configured* `EXTRACTION_TEMPERATURE` value for audit purposes — it documents the intended sampling setting without ever being sent on the request. Real sample-to-sample diversity for the multi-sample design instead comes from adaptive thinking's implicit variance (on by default for `claude-sonnet-5`), which a live test confirmed still produces genuinely differing outputs across samples.
- **Confidence in Phase 3 is exactly one signal: sample agreement.** `field_values.confidenceParts` is deliberately an extensible jsonb bag (`{sampleAgreement: 0.67}` today); the `/confidence` directory scaffolded since Phase 0 is where later signals (validator results, cross-field consistency, historical accuracy) get composed into a calibrated score. `field_values.status` is set to `'pending'` for every field this phase — auto-accept/needs-review routing against each field's `autoAcceptThreshold` is a confidence/review-phase decision, not an extraction one.
- **`field_values.validatorStatus` (`NOT NULL`) is basic type-format checking, not business-rule validation.** Per field type: `date` must `Date.parse()`, `money` must be numeric after stripping symbols, `enum` must be one of the field's `enumValues`, everything else just non-empty; `null` → `'missing'`. Deliberately does *not* check cross-field consistency (e.g. subtotal+tax=total) — the two_currencies edge case exists specifically to exercise that kind of check later, in the confidence/review phases, not here.
- **Money values are stored two ways**, discovered from a real extraction, not assumed: the model transcribes amounts as literally printed (`"$106.81"`, matching a live test against `invoice_clean_01.pdf`), but `manifest.json`'s gold-set ground truth stores the stripped form (`"106.81"`). `rawValue` keeps what the model actually said; `normalizedValue` strips currency symbols/commas for `money` fields specifically, so it's comparable to gold-set values later. Other field types pass through unchanged for now.
- **`inDevSubset` is enforced inside `extractDocument()` itself**, not just in the script that happens to only query dev-subset rows — so the one guaranteed choke point both the route and the bulk script share can't be bypassed by calling the route directly on a non-dev-subset document. Matches the explicit project rule restricting extraction to 10 documents to control API cost.
- **`FieldSpec`/`ColumnSpec` types are declared locally in `api/src/extract/schema.ts`**, structurally identical to but not imported from `scripts/fieldSpecs.ts` — `/api` should stay deployable without `/scripts` existing at runtime, and jsonb columns come back untyped from Drizzle regardless of where the TS type is declared, so there's no real coupling benefit to importing across that boundary in this direction (unlike Phase 2's scripts → api imports, which go the natural "operator script drives the app's own code" direction).
- **`PROMPT_VERSION` (`'v1'`)** stored on every `extractions` row — bumped whenever the system prompt or schema-building logic changes in a way that would make old and new extractions non-comparable for eval/gold-set purposes later.
- **`GET /documents/:id/extraction` added** (`api/src/routes/documents.ts`) to actually read extraction results back — there was no way to inspect what got extracted otherwise. Returns the *most recent* extraction for a document (ordered by `startedAt DESC` — extraction isn't deduplicated like ingestion, so a document can have several `extractions` rows over time) plus its `field_values`, with `field_value_rows` nested under table-type fields. Deliberately excludes the full `rawResponses` blob from the response (could be large; exposes only `sampleResponseCount` as a cheap audit signal that all N samples were actually stored). Built via a small Workflow: one agent implemented it, then two independent agents reviewed it in parallel — a general code reviewer, and a second agent that re-derived the correct join/ordering logic from `schema.ts` from scratch *before* looking at the implementation, to catch a subtly-wrong query without being anchored by it. Both passed the implementation; the code reviewer's one real finding (an unguarded `as unknown[]` cast on the untyped `rawResponses` jsonb column, which would 500 on a malformed row instead of degrading gracefully) was fixed before commit.
